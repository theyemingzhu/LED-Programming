# Expression scene playback contract

Status: implementation contract for the first multi-step, per-area scene slice.
Baseline inspected: `ff000001`.
Architecture: Studio authoring plus ESP32-S3 card playback; no host, Pi, or backend.

## Decision

A **scene source** is the single editable object. It owns stable area references,
ordered time steps, and independent pattern and color assignments. Studio saves
that exact source inside the normal Lightweaver project envelope. A target
compiler derives either a native card program or a recorded asset; derived
runtime data is never treated as editable source.

The first executable delivery target is a native program made from zone-aware
combo looks plus the timed playlist. This target can represent different
built-in patterns and supported card color controls on several areas at once,
then advance through a looping list of resolved states. It cannot honestly
represent arbitrary Pattern Lab evolution, full palette rendering, Movement
geometry, continuous motion across separately rendered zones, or a pixel blend
between two patterns. Those source scenes remain editable and previewable, but
their install action stays unavailable until a faithful native compiler or the
recorded path is available.

This preserves the desired interaction rather than narrowing the authoring
model to whatever happens to fit the current firmware. The title, artwork,
scene identity, selected area, and step remain continuous through edit,
preview, save, install, and reopen. Product copy can stay short because the
three authorities are visibly separate:

- **Saved** means the editable source was read back from its chosen project
  repository.
- **Trying on lights** means Studio is temporarily streaming or controlling a
  draft. It says nothing about restart behavior.
- **On card** means the exact saved source and its compiled target were read
  back from the exact card and the card reports ready playback.

## Canonical source semantics

The scene source is canonical JSON. Its eventual project location is a proposed
integration decision; when included in a project envelope it participates in
the envelope's existing SHA-256 `contentHash`. Version-1 source contains only
scene identity, defaults, ordered steps, selections, and loop intent. It does
not copy Layout geometry, target catalogs, physical ranges, or wiring.

Normalization rejects unknown major versions, a missing scene ID, duplicate step IDs,
non-finite values, and unsupported transition names. It deliberately preserves
saved selection IDs that do not resolve in the current Layout. Draft authorship
and save/reopen remain available; target resolution and compilation report the
missing areas and block delivery.

### Identity

- `id` is immutable across edits and **Update scene**. **Save as new** creates a
  new ID.
- Step IDs are stable across reorder. Target IDs come from Layout and are never
  regenerated by the scene editor.
- Exact saved-source identity comes from the containing project envelope's
  existing `contentHash`. Version 1 does not add a second scene revision,
  source hash, or layout hash before a consumer proves one is needed.

### Area references

`sceneExpressionTargets.js` is the one Layout-to-expression adapter. A scene
assignment persists its accepted selection shape, `{ areaIds, domain }`, and
rebuilds the version-1 catalog on reopen or compile:

| Catalog ID | Layout authority | Meaning |
| --- | --- | --- |
| `all` | explicit adapter ID | The whole current artwork |
| `strip:<stripId>` | current Layout strip | One strip, including a child of a divided-strip family |
| `family:<sectionFamilyId>` | `sectionFamilies` | One connected divided strip with its existing child-strip order |
| `group:<groupId>` | `layerGroups` | An explicit Layout group such as Petals or Inner ring |

`domain: "continuous"` consumes the adapter's compiled-wiring `physicalRefs`.
`domain: "repeat"` consumes its independent `instances`. The scene source does
not persist either result because wiring may change while the Layout identities
remain valid.

Missing catalog IDs and families/groups with missing members stay in the saved
selection. `resolveSceneExpressionSelection()` returns them as unresolved and
never substitutes `all` or a similarly named area. The editor offers explicit
reassignment without destroying the original reference.

The initial divided-strip fixture uses Layout's existing `sectionFamilies` plus
three separate child strips. The accepted adapter supports this today. Legacy
PatchBoard-only subranges inside one unsplit Layout strip are a later unsupported
case; they do not require a `wiringCompiler.js` redesign in the first slice.

### Steps, inheritance, and simultaneity

Each scene has one or more ordered steps. A step contains:

- `id`, `label`;
- `holdMs`, whose source meaning is visible hold after the incoming transition;
- `transitionFromPrevious`, with `mode: "cut"` or
  `mode: "dip-swap-rise"`, plus `durationMs`;
- `assignments[]`, each carrying a `{ areaIds, domain }` selection and optionally setting `pattern`,
  `color`, and `intensity` independently.

The first step begins from `defaults`. Later steps begin from the fully
resolved previous step. Omitted fields inherit; an explicit value replaces
only that field. Within one assignment, the accepted target adapter rejects
parent/child or overlapping selections before a pixel can occur twice. Across
separate assignments, proposed scene semantics resolve each field from least to
most specific: `all`, then family/group, then strip. Two same-specificity
assignments that write the same field to the same strip are ambiguous and
rejected; a strip assignment may deliberately refine a family/group field.
Catalog resolution and assignment precedence are separate operations.

The result of a step is one simultaneous state per leaf section. Changing a
pattern does not reset color. Changing color does not reset pattern, movement,
or speed. This rule is part of the source format and must be tested before any
UI is built on it.

`loop.mode` is `repeat` or `once`. The native first slice supports `repeat`.
`once` requires a defined terminal-state contract in firmware before it can be
installed. No source field is called `crossfade`: current firmware dims the
old output, swaps renderers at a nonzero floor, and raises the new output. A
true pixel crossfade would need two concurrent frames and is a separate runtime
extension.

The current playlist does not yet establish source timing equivalence for every
entry path. Automatic `playlistAdvanceToIndex()` blocks through its fade before
setting `playlistEntryStartedAtMs`, but initial play may start the already-active
look without that transition, and resume/boot paths have their own clocks.
Version-1 native lowering therefore accepts only `cut` with `durationMs: 0` and
whole-second holds. `dip-swap-rise` remains valid editable source but is not
native-eligible until a focused firmware test defines first entry, automatic
advance, manual next/previous, resume, and reboot against the source rule.

### Pattern and color values

`pattern` holds the renderer reference and motion intent:

```json
{
  "rendererId": "aurora",
  "speed": 0.8,
  "movement": { "kind": "native", "params": {} }
}
```

`rendererId` is a stable built-in or versioned renderer ID. Spatial scope comes
from the assignment selection's accepted `domain`. A continuous selection
requires a renderer whose phase domain spans the adapter's `physicalRefs`;
repeating the same pattern independently in each child is not an acceptable
substitute.

`color` keeps the authored palette separately from the renderer:

```json
{
  "palette": ["#1a0c05", "#f0a04a", "#ffe1a3"],
  "mode": "fixed-palette",
  "hueShift": 0,
  "saturation": 0.9
}
```

The native compiler may accept only values it can reproduce. Its existing zone
projection supports `patternId`, brightness, speed, hue shift, one custom hue
and saturation, Breathe, and Drift controls. A multi-color palette is not made
native by choosing its middle color. If exact palette behavior matters and no
native renderer owns it, the target is recorded or Studio-only.

## Concrete source example

This example is one connected strip divided in Layout into a `sectionFamilies`
record with three separate child strips. Step one gives the children different
simultaneous behavior. Step two selects the family as one continuous physical
domain while retaining the three independent colors, then changes only the
middle color. The requested traveling scope is preserved even though native
lowering does not yet support it. The nonzero transition is also preserved as
editable intent and rejected by the first native compiler until its clock is
proven.

### Example field-to-runtime map

| Source field | Current support | Contract handling |
| --- | --- | --- |
| `format`, `version`, `id`, `name` | Projects and project envelopes already have stable identity and content hashes | Versioned scene source; project persistence is a later integration decision |
| `selection.areaIds` | Accepted adapter resolves `all`, `strip:`, `family:`, and `group:` Layout IDs | Persist IDs unchanged, including unresolved IDs; block compile rather than save/reopen |
| `selection.domain` | Accepted adapter returns `instances` for `repeat` and compiled-wiring `physicalRefs` for `continuous` | Compiler consumes that result directly; no second target model or persisted physical ranges |
| Divided strip | `sectionFamilies` plus separate child strips are supported by the adapter | Use this model in the first fixture; legacy PatchBoard-only subranges remain later unsupported work |
| Independent pattern/color assignments | Combo looks already hold a full visual state per zone | Add source resolver/compiler; keep authored pattern and palette independent even though each derived look contains resolved snapshots |
| Three simultaneous child behaviors | Firmware `ZoneConfig` and combo looks support independent zone state | Works when every child resolves to a native zone and every renderer/color projection is faithful |
| `holdMs` | Playlist entries hold integer `dwellSeconds` from 1–3600, but start/resume paths do not yet have tested source-clock equivalence | P0 lowers whole-second holds only with zero-duration cuts; otherwise reject pending focused timing evidence |
| `cut` | `playlist.fadeMs = 0` | Works only if all native transitions use the same playlist-wide setting |
| `dip-swap-rise` | Playlist has one global `fadeMs` from 0–10000 and swaps at a nonzero floor | Editable source only in P0; native lowering waits for exact first-entry/advance/resume/reboot clock tests |
| `loop: repeat` | Timed playlist advances cyclically | Supported |
| Per-area palettes | Zone controls have one hue/saturation projection, Breathe and Drift ranges | Compile only an explicitly faithful subset; full palettes require a native palette renderer or recording |
| Continuous family selection | Adapter already supplies exact physical-order references | Native renderer/runtime support is still required; do not silently repeat per child |
| Movement | Lab preview transforms geometry; ordinary native look conversion omits it | Resolve as described below before native eligibility |

## Target classification

Every saved scene source receives a target report derived from the source,
current Layout, and the connected card descriptor. The report is not stored as
authoritative source; it is reproducible build evidence.

### Native program: current primitives with pure compiler gates

The current building blocks are real:

- a combo look can give each runtime zone an independent built-in pattern and
  supported visual controls;
- firmware can play up to 16 timed playlist entries, with integer-second dwell,
  one global transition duration, and looping, but full source-clock equivalence
  has not been tested across initial play, advance, resume, and reboot;
- the hardware contract permits 65,535 physical pixels, 12 zones, six ranges
  per zone, four outputs, and a 3,968-byte config payload;
- native Color Journey capability versions can cover 4,096 pixels, but Color
  Journey is a special compiled whole-look path rather than proof of arbitrary
  per-area multi-step recipes.

The first native compiler may therefore accept a scene only when:

1. Layout resolves to at most 12 leaf runtime zones and six ranges per zone;
2. every step resolves to built-in renderer IDs and color/movement behavior the
   card reproduces exactly;
3. there are at most 16 steps;
4. holds are whole seconds from 1–3600;
5. every transition is `cut` with `durationMs: 0` in P0;
6. the complete serialized config fits 3,968 bytes; and
7. the connected card advertises every required capability.

The compiler emits one derived combo look per step and a playlist entry that
references it. IDs derive from scene and step IDs, so updates replace the same
runtime objects rather than accumulating copies. The compiler does not mutate
the source into `looks[]` or `playlist[]`; where the source will live in the
project is outside P0.

The 4,096-physical-pixel reference is mandatory in compiler tests. Pixel count
alone does not block native playback, but zone/range count, native recipe
capabilities, and the 3,968-byte config ceiling still can.

### Recorded program: required for richer fidelity, unavailable for this case today

`.lwseq` records final RGB frames and can preserve Pattern Lab layers, palettes,
and Movement without teaching firmware their source semantics. Firmware already
validates sequence size, hash, channels, exact physical pixel count, FPS, and
frame count, then loops the whole canvas from SD. Sequence looks can be playlist
entries, but they are whole-canvas and not zone-targetable.

The current authoring/install path is not sufficient for the 4,096-source-pixel
reference:

- the baker hard-stops above 1,024 **source** pixels;
- a physical frame may contain up to 4,096 pixels in the current sequence
  manifest, but a 4,096-pixel source layout still fails before render;
- normal runtime packaging ignores `sequenceAssets`;
- the generated SD package contains one sequence project rather than a combined
  native/recorded program;
- there is no browser sequence upload endpoint; installation is the manual
  FAT32 microSD unpack flow;
- ten minutes at 24 FPS and 4,096 RGB pixels is about 177 MB before package
  overhead, so raising the source cap alone is not a solution.

Recorded delivery requires bounded-memory rendering, storage/capacity planning,
combined package construction, resumable asset transfer or an explicit SD
workflow, asset readback, replacement, and hardware playback evidence. It does
not justify a host or Pi.

### Studio-only

A scene is Studio-only when neither target is faithful. It remains fully saved
and reopenable. The editor shows a short reason at the install action and keeps
the source intact. Simplification always creates an explicit variant; it never
rewrites the owner's source or reports an approximation as installed.

## Movement and preview fidelity decision

The native milestone must use a target-faithful preview. For a native-eligible
scene, Studio previews the **compiled combo looks and playlist semantics**, not
the richer Pattern Lab renderer. This makes zone boundaries, reduced card color
controls, holds, and the actual dip–swap–rise transition visible before install.

Movement then has three honest outcomes:

1. A Movement setting maps to documented native renderer parameters with the
   same phase and geometry semantics. The compiler includes it and the target
   preview uses those parameters.
2. The recorded renderer captures it exactly and the scene is classified for
   recorded delivery.
3. Neither target can reproduce it. The scene remains Studio-only with
   `movement-not-supported-by-card`.

The first slice uses outcome 3 for non-default Lab Movement. Copying only
color/brightness/speed, as `resolvePatternLabVisualLook()` currently does,
cannot be called faithful. A `continuous` selection follows the same rule until
a native renderer consumes the adapter's physical-order domain faithfully.

Live preview is a separate transport. It may stream the rich source renderer
for rehearsal, but the UI must label that state **Trying on lights** and retain
the compiled target preview as the install comparison. Stopping the stream,
closing the browser, or the card watchdog returning to its installed look does
not change installation status.

## Save, install, interruption, and reopen

### Browser/project save

Scene edits update the project working copy and mark it changed. A committed
save writes a complete project envelope through the existing guarded repository
path and reads back the envelope `contentHash`. Recovery autosave is not a
committed save. Reopening selects the same scene ID, restores all step and area
IDs, and recomputes target eligibility from the current Layout/card descriptor.

### Delivery authority: reuse existing evidence first

No new wire or firmware status field is approved by this contract. P1 must
first evaluate whether the existing authorities can prove the complete flow:

1. The project repository already commits and reads back a complete editable
   project envelope by exact SHA-256 `contentHash`.
2. `prepareCardDeployment()` already derives a runtime fingerprint and carries
   project revision/fingerprint from one project snapshot.
3. `verifyCardDeployment()` already checks the exact card, revision/fingerprint,
   and ready state. `verifyCardPostSaveState()` additionally checks known-good
   wiring plus required installed look and zone IDs.

The proposed orchestration is to freeze one project snapshot, save/read back
its envelope, compile the runtime from that same snapshot, install it, then
perform the existing runtime and look/zone readbacks. If those identities can
be correlated without a race, they are sufficient and the wire contract stays
unchanged. If an implementation test proves a gap, the manager must approve the
smallest additional binding before firmware or schema work starts. Candidate
fields such as a source head or compiled-target hash are proposals, not accepted
requirements.

Source-first sequencing remains the preferred P1 behavior because a compile or
runtime failure then leaves the previous known-good playback intact. An
interruption may leave newer editable source on the card while the previous
runtime is active; that state is **Saved on card — not installed**.

Installation becomes **On card** only after fresh existing evidence proves:

- exact `cardId`, project ID/revision/fingerprint, and no conflicting wiring
  candidate;
- `knownGoodProject`, `commandReady`, `runtimePhase: ready`, `playbackReady`,
  and `outputReady`;
- the expected editable project envelope was read back by `contentHash`; and
- every required compiled look and zone ID is present.

Recorded delivery additionally needs its existing manifest/file hash and the
firmware sequence-open validation to be observable. Whether that needs new
status evidence is also a later manager decision. A UI success callback or a
successful POST is never proof.

### Interrupted install and reopen reconciliation

- Before source commit: retain the previous source head and runtime; the draft
  remains in browser recovery.
- After source commit but before runtime verification: keep the previous
  installed record and show **Saved on card — not installed** for the new saved
  source. Retry may resume from the verified source head.
- After runtime commit but before Studio receives the reply: do not guess.
  Reconnect and repeat the existing project-envelope, runtime, look, zone, and
  wiring readbacks. Promote to **On card** only if they correlate to the frozen
  install snapshot.
- On reload, persisted installation records begin unverified, as they do now.
  Fresh exact-card evidence re-verifies them. If source and runtime evidence do
  not correlate, show **Needs verification** or **Changes not on card** and keep
  both copies available.
- A failed update never deletes or relabels the previous known-good runtime.
  Head conflicts offer compare/keep-both/replace through the existing project
  repository contract; scene code does not invent another conflict model.

## Minimal vertical slice

### P0 — pure source resolution and target compilation

P0 changes no project schema, wiring compiler, runtime packager, firmware, or UI.
It builds only pure scene semantics and fixtures around the accepted target
adapter:

- reuse `lightweaver/src/lib/sceneExpressionTargets.js` unchanged as the sole
  Layout catalog/selection authority;
- `lightweaver/src/lib/sceneExpression.js`: normalize version-1 source while
  retaining unresolved selections, resolve step/field inheritance, and reject
  only semantic conflicts that do not require current Layout;
- `lightweaver/src/lib/sceneExpressionNative.js`: consume adapter results,
  classify fidelity, and compile supported source to deterministic combo-look
  plus playlist data without writing it into a project.

Focused tests:

- `sceneExpression.test.js`: the two-step example resolves pattern and color
  independently, reorders by stable step ID, distinguishes within-selection
  overlap from across-assignment precedence, and round-trips unresolved IDs;
- extend `sceneExpressionTargets.test.js` with a `sectionFamilies` divided-strip
  fixture, a mandala group, changed/missing members, continuous physical order,
  and repeat instances;
- `sceneExpressionNative.test.js`: deterministic derived IDs, 16-step/config
  limits, whole-second cut-only timing, faithful-color gates, Movement rejection,
  unresolved-target rejection, and a 4,096-physical-pixel fixture.

Exit: normalization preserves the full example even with missing current areas.
Against its valid Layout fixture, step one resolves to a compilable state when
its colors use the supported native projection. Step two reports both unsupported continuous native
rendering and unproven nonzero-transition timing; neither is silently changed. A
cut-only repeat-domain variant compiles deterministically at 4,096 physical
pixels.

### P1 — connected novice journey and exact authority

Add the scene collection/editor actions with one stable title area and one
primary action per state. The likely integration files are
`PatternLabScreen.jsx`, `lw-pattern.jsx`, `app.jsx`, `cardDeployment.js`, and
`projectLifecycle.js`, plus focused browser coverage in a new
`expression-scene-lifecycle.spec.ts`.

First decide the project persistence location and integrate the pure compiler
through the existing project/runtime builders. Then test whether the current
project `contentHash`, runtime revision/fingerprint, readiness, and look/zone
readbacks prove exact delivery. Extend card project repository and deployment
tests for source-first delivery, head conflict, lost response, readback
reconciliation, and previous-runtime preservation. Any project schema, wire,
runtime status, or firmware addition remains a proposed manager decision backed
by a demonstrated evidence gap.

Exit: create, save, reopen, try on lights, install, close the browser, reconnect,
and reopen the same editable scene with truthful independent Saved / Trying /
On card states. A browser test blocks all real card networking; it proves the
journey and evidence handling, not physical light output.

### P2 — recorded 4,096-pixel delivery

Treat this as a separate implementation scope. Extend `lwseqBake.js`, worker
budgets, sequence packaging, SD/asset installation, and firmware status only
after memory and storage budgets are explicit. Do not unlock install merely by
raising `finalSamples` from 1,024.

Required Bench observations before claiming standalone expression playback:

1. A physical strip divided into three sections shows the three simultaneous
   native behaviors and the next step at the expected hold/transition timing.
2. A mandala fixture addresses only the explicitly named center/ring/petal
   groups; no strip or radial inference appears.
3. The card loops for at least ten complete cycles with Studio closed, then
   resumes the intended step behavior after a power cycle.
4. Interrupt source upload, runtime staging, and post-commit verification in
   separate runs; the previous known-good runtime remains playable and reopen
   reports the recoverable state accurately.
5. Read the project back from the card on another browser/profile and reopen
   the exact scene source, including IDs, both steps, area assignments, and
   hashes.
6. For recorded work, verify a 4,096-pixel asset's exact hash/size, sustained SD
   playback, replacement, restart, and failure behavior. Compare physical
   color, motion, gamma, order, and current limiting with the target preview.

No Bench item is marked passed by automation or this contract.

## Architectural boundaries for the builder

- Keep Show's audio-reactive engine live and browser-hosted. A future named
  performance may reference a scene source, but it is not this standalone
  playback contract.
- Keep volatile live knobs outside the project fingerprint until the user
  commits a scene edit. Preview never mutates the installed source binding.
- Do not introduce a second layout model in Lab. All spatial references resolve
  through `sceneExpressionTargets.js` and its current Layout catalog.
- Do not put editable source inside `.lwseq`; its manifest snapshot is
  provenance. Reopen uses the project envelope.
- Do not add arbitrary crossfade language or emulate unsupported Movement,
  palettes, or continuous phase with a visually different native setting.
- Do not route card commands through a public backend. Source storage, runtime
  installation, and status readback remain direct exact-card operations.
