# Studio project compatibility

Studio opens flat version 1 and 2 project JSON, nested version 3 project JSON, and the version 1 repository envelope around a supported document. The file picker accepts `.lw.json`, `.lwproj.json`, and `.json`. New backups use `.lw.json` and the current version. A file with a newer project or envelope version needs a Studio version that supports it. An older format cannot supply information it never saved. In particular, the flat fixtures have no stored project ID or GPIO assignment. Studio assigns an ID on first open and supplies default wiring for review. The ID persists in subsequent saves.

A current browser recovery draft takes priority over the saved library copy. A readable saved copy can recover a damaged autosave. The retired layout key can supply a missing drawing for an untouched starter, while an intentional empty layout, existing SVG, saved looks, recordings, or a custom playlist takes priority. Keep older raw storage available during migration. Project file validation runs before replacement or changing the active save destination. Portable recording bytes retain their original hash and topology metadata. Studio verifies the whole bundle before storing its recordings. Some historical recordings must be re-recorded before card playback even though their editing source and exact bytes remain portable.

Card reconstructions and runtime packages serve different purposes. A reconstructed project can lack original artwork, and Projects retains its partial-copy label. The compatibility promise applies to Studio projects, including these labeled partial copies. Card runtime configuration, signed production packages, and the separate Mapper format have their own import paths.

When changing the project format, preserve fixtures from older producers. Test load, edit, save, reload, a fresh-browser file round trip, and rejection without changes to the current workspace. Add a new version when an older reader cannot safely preserve the meaning of the file. Keep the migration idempotent and check its normalized result against values from the old producer. Unit tests run in `test:unit` and the file/browser journeys run in `test:projects:browser` through the launch gate and cloud CI lane.
