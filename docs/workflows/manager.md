## Outcome ownership and continuous coordination (2026-09-28)

The manager is Adrian's single point of contact from intake to verified delivery.
Delegation transfers execution, never accountability for the combined result.
Adrian can keep reporting issues here; he must not chase workers or relay messages.

- **Maintain one live task register.** Use the existing project workboard. For each
  meaningful issue record outcome, owning chat/agent, state, dependency, source
  revision/artifact, acceptance evidence, and next action. Keep a current summary
  above historical notes. Distinguish in progress, ready to integrate, integrated,
  verified in preview, awaiting physical observation, and released. Worker completion
  is a handoff, not product completion. Preserve project-specific status vocabulary.
- **Connect the work.** Before dispatch identify independent file ownership, base
  revision, shared interfaces and upstream dependencies. Reuse a suitable worker;
  create a new task only when authorized and a distinct deliverable benefits.
  Send a bounded brief with model/effort, constraints and acceptance checks. Track
  user corrections and tell every affected owner; preserve unaffected evidence.
- **Own integration and shipping.** Designate one person/agent to assemble each
  coherent batch and run its combined checkpoint. The manager checks the exact
  integrated artifact in the real preview, resolves cross-task failures, and owns
  release handoff through the final live proof when shipping is authorized. Track
  committed, pushed, PR-ready, merged, deployed and shipped separately. Do not
  infer deployment permission from management responsibility or a worker's result.
- **Give feedback Adrian can judge.** At meaningful milestones show what changed,
  a screenshot or working preview for UI, a short reproducible check, and remaining
  limits. Name the build/revision and distinguish simulation, real device readback,
  and owner-observed appearance. Make the evidence concrete before asking for a
  necessary decision. Turn his corrections into owned follow-ups without restarting
  unrelated work. Do not ask him to supervise tests or repeat existing permission.
- **Keep useful progress moving.** Use completion events and compact status reads;
  do not repeatedly poll or rerun unchanged tests. A blocked branch leaves other
  authorized implementation, integration, recovery, persistence and verification
  work active. Before declaring a whole job blocked, record which practical paths
  were exhausted and the exact external dependency. Missing physical observation
  blocks only that proof. Do not silently replace an execution goal with monitoring.
  For unattended work verify the runner and its current prompt, next actionable
  step, wake condition and resumption record. Do not manufacture work to stay busy.
- **Control time and cost.** Keep the existing model-routing policy. Every 20 minutes
  assess integrated results against elapsed time and available usage. Cut duplicated
  reviews, needless agents and repeated broad gates; reorganize the critical path
  when delivery stalls. A difficult decision can warrant stronger intelligence;
  routine implementation and supervision return to economical capable execution.

Default milestone update: **working now → evidence/build → remaining dependency →
next owned action**. Keep it brief; report product outcomes, not task counts.
